# API contracts (V1)

Base: `https://api.jomhor.ma/v1`. JSON, UTF-8. Money in integer centimes (`_mad`).
Times in RFC 3339 UTC; clients show and enter them in the venue's `timezone` (IANA), never a fixed offset. Errors: `{ "code": "ORDER_EXPIRED", "message": "...", "details": {} }`.

Three audiences, three auth schemes:

| Audience | Auth | Prefix |
| --- | --- | --- |
| Fan (app, web shop) | Bearer JWT from phone-OTP login, carrying a revocable session `sid`; `GET /fan/organizers*` and `GET /fan/events*` are public | `/fan/...` |
| Organizer (back-office) | Bearer JWT, staff account, `X-Organizer-Id` | `/org/...` |
| Gate (scanner) | Device signature, ECDSA P-256 key in Android Keystore (§Gate auth). No server session: staff PINs are checked on the device (§Gate PINs) | `/gate/...` |
| Payment providers (card/wallet gateway, cash networks) | Provider signature, verified per provider | `/payments/...` |

Error codes (Lot 0 to Lot 5; later lots add theirs here):

| Code | HTTP | When |
| --- | --- | --- |
| `VALIDATION_FAILED` | 422 | Bad body; `details.fields{}` |
| `BAD_REQUEST` | 4xx | Request rejected by the framework before reaching a handler (bad path/query type, missing header, wrong method or media type); HTTP status kept |
| `INTERNAL_ERROR` | 500 | Anything unexpected; fixed message, `details: {}`, logged server-side, never echoes the exception |
| `UNAUTHORIZED` | 401 | Missing, invalid or wrong-audience token; fan token whose session is revoked or expired; gate: missing or bad device signature, unknown device, bad or expired `enrol_code` (fixed message, empty `details`) |
| `DEVICE_CLOCK_SKEW` | 401 | `X-Device-Time` more than 5 min from server time; `details.server_time`. The device fixes its offset and retries once |
| `FORBIDDEN` | 403 | No active staff row for `X-Organizer-Id`, or role not allowed |
| `DEVICE_NOT_ACTIVE` | 403 | Device `PENDING` or `REVOKED`; `details.status`. On `REVOKED` the scanner wipes K_e, manifest, staff list and scans |
| `NOT_FOUND` | 404 | Unknown id, or an id of another organizer or user |
| `OTP_INVALID` / `OTP_EXPIRED` | 401 | Verify failed |
| `OTP_RATE_LIMITED` | 429 | Any OTP limit in §Fan auth (per phone, per IP, or phone locked after failed codes) |
| `EVENT_NOT_ON_SALE` | 409 | Order outside the sale window. `details.reason`: `NOT_ON_SALE` (status), `NOT_STARTED` (+ `details.sale_starts_at`), `CLOSED` (at or after `refund_cutoff_at`). **Lot 5 step 2:** `NOT_STARTED` also between two phases (the current phase is `SCHEDULED`; §Waiting room Phases): `details.sale_starts_at` = that phase's sale start. **Lot 5 step 4:** invitations: `NOT_ON_SALE` when the event isn't `ON_SALE`/`GATES_OPEN`; `CLOSED` at or after its `transfer_until` (+ `details.transfer_until`). |
| `EVENT_NOT_EDITABLE` | 409 | Event PATCH, price write, promo-code create (Lot 5 step 4) or publish when the status doesn't allow it (PATCH, prices and promo codes: only `DRAFT`/`ON_SALE`; publish: only `DRAFT`, so the losing side of a double publish gets it too); close outside `ON_SALE`/`GATES_OPEN` (`details.reason` `NOT_OPEN`) or before `starts_at` (`NOT_STARTED` + `details.starts_at`); assignment PUT on a `CLOSED` event **Lot 5:** + `details.reason` `ROOM_STARTED`: event PATCH moving `sale_starts_at` while its room is past `SCHEDULED` and not `ENDED`. **Lot 5 step 3:** `details.reason` `PASS_TICKETS`: event PATCH changing `series_id` once a pass ticket order exists for the event |
| `SOLD_OUT` | 409 | `details.price_category_id`, or `details.product_id`: a pass product's `quota` is reached |
| `PER_ACCOUNT_LIMIT` | 409 | `details.limit`, `details.held`; **Lot 4:** + `details.field` (the holder path) when a split-pay member is over their own limit. **Lot 5:** `details.reason` `HOLDER`: a holder account (the buyer's own places included), or a transfer's recipient, would hold more than `per_account_limit` places of the event. Then `details.field` (the holder path, or `to_phone`) and `details.limit` only, never `held`. |
| `MEMBERS_ONLY` | 409 | A place of a `MEMBERS` price category whose holder isn't a live member of the organizer who joined before the event's `sale_starts_at`. `details.field` (the holder path), `details.member_joined_before` (the event's `sale_starts_at`, or null when it has none). **Lot 5 step 3:** + `details.paid_required` (bool, the organizer's, §Products Paid membership). |
| `PROMO_REFUSED` | 409 | **Lot 5 step 4:** `POST /fan/orders` with a `promo_code` that can't apply (§Promo codes). `details.field` `promo_code`, `details.reason`:<br>• `UNKNOWN`: no active code with that text for this event (an inactive code reads the same);<br>• `NOT_APPLICABLE`: none of the buyer's own places is in the code's scope, or the discount would be 0;<br>• `USED_UP`: the code's `max_uses` is reached;<br>• `ACCOUNT_LIMIT`: the caller's uses reached `per_account_max`.<br>No count, cap or other detail. |
| `SALE_BUSY` | 429 | Basic on-sale queue is full; `details.retry_after_s` (int, 5–30, with jitter). Retry the same request. **Lot 5:** With a room it remains a safety net for admitted fans. |
| `ADMISSION_REQUIRED` | 409 | `POST /fan/orders` on an event whose room is `PRE_QUEUE`, `OPEN` or `PAUSED` (or still `SCHEDULED` past `sale_starts_at − pre_queue_min`: the check fails closed while the tick catches up), without a valid `X-Admission-Token`. `details.reason`: `MISSING`, `INVALID` (bad signature, another user, another event, or a room that isn't the event's current phase), `EXPIRED`. Clients go to the room |
| `QUEUE_NOT_OPEN` | 409 | Join refused. `details.reason`: `NO_ROOM`, `NOT_STARTED` (+ `details.opens_at`), `ENDED` (buy without the room), `CLOSED` (sales closed) |
| `NOT_ELIGIBLE` | 409 | Join, or a split `pays` member, fails the room's rule. `details.reason`: `ACCOUNT_TOO_NEW` (+ `details.verified_before`), `NOT_MEMBER` (+ `details.member_joined_before`), `NOT_ENOUGH_EVENTS` (+ `details.min_events_attended`, `details.attended`). For a split `pays` member: `details.field` (the holder path) only, no reason and no rule figures, so a buyer can't learn another phone's account age, membership or attendance. **Lot 5 step 3:** `NOT_MEMBER` + `details.paid_required` |
| `QUEUE_DEVICE_LIMIT` | 409 | This device already holds `details.limit` entries of other accounts in the room |
| `QUEUE_RATE_LIMITED` | 429 | `details.reason`: `IP` (a join that would create or move back an entry: too many from this IP in the room in 5 min) or `POLL` (the same entry polled again within 1 s); `details.retry_after_s` (int). Wait that long, then retry; a poller then resumes its `poll_after_s` rhythm |
| `ROOM_STATUS` | 409 | Room phase PUT changing anything but `admission_rate_per_min` once the room has left `SCHEDULED`, or pause/resume/end in the wrong status; `details.status` |
| `WAITLIST_CLOSED` | 409 | Waitlist join refused. `details.reason`: `NOT_SOLD_OUT` (places are left: buy), `ROOM` (a waiting-room phase isn't `ENDED`: use the room), `CLOSED` (the event isn't inside its sale window). |
| `PRODUCT_NOT_ON_SALE` | 409 | Product order at or after the product's `sales_close_at`; `details.sales_close_at` |
| `PASS_HELD` | 409 | The caller already has a pass of the series that isn't `CANCELLED`; `details.pass_id`, `details.status` (a `PENDING` one: resume its order from `GET /fan/passes`) |
| `MEMBERSHIP_PAID` | 409 | The caller's `paid_until` is already ≥ the product's `valid_until`; `details.paid_until` |
| `PASS_STATUS` | 409 | **Lot 5 step 3b:** installment on a pass that isn't `ACTIVE` or `SUSPENDED` (`details.status`), or with nothing left to pay (`details.reason` `PAID_UP`) |
| `TICKET_NOT_VALID` | 409 | PDF, WhatsApp re-send, transfer or re-issue of a ticket that isn't `VALID`. **Lot 5 step 3b:** the effective status (§Passes Effective status) counts |
| `TRANSFER_CLOSED` | 409 | Transfer or re-issue at or after the ticket's `transfer_until` (`refund_cutoff_at − tickets.transfer.close-before-cutoff`, default 30 min; no cutoff set = closed); `details.transfer_until` |
| `DELIVERY_RATE_LIMITED` | 429 | More than 3 WhatsApp re-sends of one ticket in 24 h |
| `ORDER_EXPIRED` / `ORDER_NOT_PAYABLE` | 409 | Pay on an order that isn't `RESERVED` or `AWAITING_CASH`, or whose hold has passed |
| `METHOD_NOT_AVAILABLE` | 409 | `/pay` with a method this order can't use now. `details.reason`: `TOO_LATE` (cash: the code would be valid less than `payments.cash.min-window`; + `details.sales_close_at`), `CASH_CAP` (§Cash codes cap), `NOT_CONFIGURED` (no provider for WALLET; for CASH_AGENCY: no cash point and no network) |
| `CODE_NOT_PAYABLE` | 409 | Collect on a code that isn't payable (§Cash codes); `details.status` = the order status, or `EXPIRED` when the hold has passed |
| `POS_SESSION_REQUIRED` | 409 | POS sale, collect or print without an open till session of the caller |
| `POS_SESSION_CLOSED` | 409 | Close of a session already closed |
| `CODE_TAKEN` | 409 | Duplicate zone or gate code in a venue |
| `VENUE_IN_USE` | 409 | Changing a venue's `timezone` once events reference the venue |
| `ZONE_IN_USE` / `GATE_IN_USE` / `PRICE_IN_USE` | 409 | Delete of a referenced row. `gate_zones` mappings do not count: they are removed with their zone or gate. References are price categories, order items, tickets. Lot 2: device assignments and scans reference gates. |
| `QUOTA_EXCEEDS_CAPACITY` / `QUOTA_BELOW_SOLD` | 422 | Price category quota rules |
| `TICKET_STATUS` | 409 | Block of a non-`VALID` ticket, unblock of a non-`BLOCKED` one, refund of a ticket that is neither; `details.status`. **Lot 5 step 3b:** unblock of a ticket that is `BLOCKED` only through its suspended pass: `details.reason` `PASS_SUSPENDED` |
| `REFUND_FROZEN` | 409 | Block, unblock or refund at or after `refund_cutoff_at` (or with no cutoff set); checked before the status, so it wins over `TICKET_STATUS` |
| `DEVICE_REVOKED` | 409 | Approve on a `REVOKED` device |
| `DEVICE_IN_USE` | 409 | Assignment PUT that removes a device with scans on the event; `details.device_ids` |
| `MANIFEST_NOT_READY` | 409 | Before `manifest_available_at`, or no version built yet; `details.available_at` |
| `EVENT_CLOSED` | 409 | Manifest request on a `CLOSED` event |
| `EVENT_NOT_CLOSED` | 409 | `closed-ack` before the event is `CLOSED` |
| `CAMPAIGN_STATUS` | 409 | Campaign PATCH or send outside `DRAFT`, cancel outside `SCHEDULED`; `details.status` |

No pagination in Lot 0. Lists are per organizer and small, in a stable order: by name for
venues, by code for zones and gates, by `starts_at` for events, by `zone_id` then `name` for prices,
ids ascending inside arrays such as `zone_ids`. Integer fields reject floats and strings (`50.5`,
`5000.0`, `"5000"` → 422).

Conventions: create → `201` with the resource; delete → `204`; PATCH is partial (a missing or
`null` field is left unchanged; send `""` to clear an optional text field such as `city`) and
returns the same representation as the matching GET.

## Fan

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/fan/auth/otp` | `{phone}` (E.164) → `202`. 6-digit code, valid 5 min, 5 attempts per code. Fan codes are limited per phone to 3 sends per 10 min and 10 per 24 h. After 15 failed verifications in 24 h the phone is locked for fan login until the oldest failure is 24 h old. Per IP (resolved through trusted proxies only): 60 sends per 10 min, 600 per 24 h. Over any limit → 429 `OTP_RATE_LIMITED`. The code is sent after commit, off the request thread: `202` means accepted, not delivered. |
| POST | `/fan/auth/verify` | `{phone, code}` → `{token, expires_at, user:{id, phone, display_name, locale}}`. Creates the user on first login and a fan session every time. JWT `aud=fan`, `sid` = session id, 30 days. Only a fan code verifies here. Locked phone → 429 `OTP_RATE_LIMITED`. The first successful fan verify of a user sets `users.verified_at`. |
| GET, PATCH | `/fan/me` | `{id, phone, display_name, locale}`. PATCH `{display_name?, locale?}`: `display_name` per §Holder names, `locale` ∈ `fr`, `ar`, `en`. |
| POST | `/fan/me/logout` | `{all?: boolean}` (body optional; absent = `all: false`) → `204`. Revokes this session, or all the user's sessions when `all`. The app wipes its cached tickets and K_t. |
| GET | `/fan/organizers` | **Public: send no `Authorization` header.** The club directory: listed organizers (`slug` set), by `name` then `id` → `[{id, slug, name, kind, crest_url}]` (§Club directory). |
| GET | `/fan/organizers/{slug}` | **Public.** One listed organizer, same shape. Unknown, unlisted or malformed slug → 404. |
| GET | `/fan/events?organizer=&from=` | **Public: send no `Authorization` header.** Events with status `ON_SALE` or `GATES_OPEN` and `starts_at >= from` (default now), by `starts_at` then `id`, at most 50. `organizer` (an organizer id) may be repeated (`?organizer=a&organizer=b`): the events of those organizers, listed or not. Absent: the events of every **listed** organizer (§Club directory). Each: `{id, organizer_id, organizer:{slug, name, crest_url}, status, event_type, title, starts_at, doors_open_at, timezone, venue:{name, city}, metadata, sale_starts_at, sales_close_at, on_sale, sold_out, from_price_mad, per_account_limit}`. `sales_close_at` = `refund_cutoff_at`. `status` = the event status (`ON_SALE`, `GATES_OPEN`, `CLOSED`), so clients never infer it. `on_sale` = ON_SALE and inside [`sale_starts_at`, `sales_close_at`). `sold_out` = every category has `remaining = 0`. `from_price_mad` = lowest `price_mad` among categories with `remaining > 0`, null if none. `organizer` per §Club directory; `organizer.slug` is null for an unlisted organizer. **Lot 5:** each event + `room: {phase, label, status: SCHEDULED\|PRE_QUEUE\|OPEN\|PAUSED, opens_at, sale_starts_at, eligibility: {verified_before, member_joined_before, min_events_attended} \| null, next: {phase, label, opens_at, sale_starts_at} \| null} \| null`. It describes the event's **current phase** (§Waiting room Phases), and is null when the event has no phase or every phase is `ENDED`. `sale_starts_at` and `opens_at` are that phase's: `opens_at` = `sale_starts_at − pre_queue_min`. `next` is the following phase not `ENDED`. `eligibility` as before, from the phase's rule: `verified_before` = `sale_starts_at − min_account_age_days` (RFC 3339, or null); null when no rule is set. **Lot 5 step 2:** `from_price_mad` = the lowest `price_mad` among categories with `remaining > 0` **and `audience = ALL`**, null if none. `sold_out` unchanged. |
| GET | `/fan/events/{id}` | **Public.** Same fields + `zones:[{id, code, name, seated, gate_codes[], prices:[{price_category_id, name, price_mad, remaining}]}]`; zones by `id`, prices by `name`, `gate_codes` ascending. `remaining = quota − sold`. `DRAFT` (or unknown) → 404; `CLOSED` is returned with `on_sale = false`. No key, no `sold`/`quota` fields. **Lot 3:** + `payment_methods`: subset of `["CARD","WALLET","CASH_AGENCY"]` in that order. `WALLET` iff a wallet provider is configured. `CASH_AGENCY` iff the organizer has a cash point or a network is enabled, and `now < refund_cutoff_at − payments.cash.min-window`. Plus `cash_until`: `refund_cutoff_at − payments.cash.min-window` when cash is set up for the organizer (null otherwise), so clients show cash as "Trop tard pour le cash" after it and hide it when null; a code bought now is valid until `least(now + 24 h, refund_cutoff_at)`. The cash cap is not reflected (`/pay` answers it). **Lot 5 step 2:** each `prices[]` + `audience: ALL\|MEMBERS`. |
| POST | `/fan/queue` | `{event_id, device_id}`. `device_id` = 16–64 chars `[A-Za-z0-9_-]` (422). Checks in order: event visible as in `GET /fan/events/{id}` (404); room `PRE_QUEUE`, `OPEN` or `PAUSED` (a room still `SCHEDULED` past `sale_starts_at − pre_queue_min` counts as started), and sales not closed (409 `QUEUE_NOT_OPEN`); eligibility (409 `NOT_ELIGIBLE`); device limit (409 `QUEUE_DEVICE_LIMIT`); per-IP limit, only when an entry is created or moved back (429 `QUEUE_RATE_LIMITED` `IP`). The caller's entry already exists → `200` with it and a fresh queue token, unless its turn has `EXPIRED`: then it is moved to the back (`rank` and `admitted_at` cleared, `joined_at = now()`) → `201`. New → `201`. → the `GET /fan/queue` shape. **Lot 5 step 2:** joins the event's current phase. `QUEUE_NOT_OPEN`: `NO_ROOM` (no phase), `ENDED` (every phase `ENDED`), `NOT_STARTED` + `opens_at` (the current phase is `SCHEDULED`). An entry in an earlier phase doesn't carry over: the new phase creates a new entry. |
| GET | `/fan/queue` | Header `X-Queue-Token`; send no `Authorization` header (ignored). Missing, bad or expired token, or a purged entry → 401 `UNAUTHORIZED`. The same entry polled again within `rooms.poll-min-interval` (1 s) on one instance → 429 `QUEUE_RATE_LIMITED` `POLL` (no database read). CORS: allowed from `SHOP_ORIGIN`, no credentials. → `{event_id, status, sale_starts_at, position, in_room, rate_per_min, estimated_wait_s, sold_out, admission: {token, expires_at} \| null, queue_token, poll_after_s, server_time}`. `status`: `PRE_QUEUE` (before the draw; position null), `WAITING` (position null until ranked), `ADMITTED`, `EXPIRED`, `PAUSED`, `ENDED`. `position` = `rank − admitted_through` (≥ 1) while waiting. `in_room` = `ranked_count − admitted_through`, or `joined_count` before the draw. `rate_per_min` = `measured_rate_per_min` (0 when paused). `estimated_wait_s` = ⌈position × 60 ÷ rate_per_min⌉, or null when the rate is 0 or the position is null. `sold_out` per §Waiting room. `admission` only while `ADMITTED`. `queue_token` = refreshed (it carries the rank once known). `poll_after_s` per §Waiting room. `Cache-Control: no-store`. **Lot 5 step 2:** `ENDED` also when the token's room is no longer the event's current phase. Clients then re-read `GET /fan/events/{id}`: a `room` means the next phase (join it), null means buy without a room. |
| POST | `/fan/orders` | `{event_id, channel: APP\|WEB, items:[{price_category_id, qty, holders:[{name, phone?}]}]}` → `201 {id, status: RESERVED, reserved_until, total_mad, items:[{price_category_id, zone_id, zone_name, name, qty, unit_price_mad, holders:[{label}]}]}`. Held 8 min. Item `name` = the price category, `zone_name` = the zone. Checks in order: event (404), sale window (409 `EVENT_NOT_ON_SALE`), items and holders (422), queue (429 `SALE_BUSY`), per-account limit (409), quota (409 `SOLD_OUT`). `holders.length = qty` (else 422 on `items[i].holders`). `name` per §Holder names (422 on `items[i].holders[j].name`). `phone` absent or equal to the buyer's → the buyer holds that ticket. Another E.164 phone → that phone's account holds it (created if new); it gets the ticket on WhatsApp and in the app or W5 after OTP login, and the buyer never gets its K_t or PDF. The limit counts places in the buyer's `RESERVED`, `AWAITING_CASH` and `PAID` orders for the event, **minus the `REFUNDED` tickets of those `PAID` orders** (Lot 5 step 2; also for a split member's own limit), ≤ `per_account_limit`. **Lot 4:** `holders:[{name, phone?, pays?}]`; `pays: true` = split pay (§Split pay). The response + `group: {role: INITIATOR, members:[{order_id, holder_label, places, total_mad, status, reserved_until, pay_url}]} \| null`. **Lot 5:** Checks in order: the body's shape (422, no SQL); **admission** (from the per-instance memo and the token's signature, before any database read of the request; a `DRAFT` event is refused here from the memo with 409 `EVENT_NOT_ON_SALE` `NOT_ON_SALE`, the same answer as the event check, so a draft's room and sale start never leak): when the current phase is `PRE_QUEUE`, `OPEN` or `PAUSED`, header `X-Admission-Token` for that phase's room, else 409 `ADMISSION_REQUIRED`; when the current phase is `SCHEDULED`, 409 `EVENT_NOT_ON_SALE` `NOT_STARTED` with that phase's `sale_starts_at`; event (404); sale window (409 `EVENT_NOT_ON_SALE`); items and holders (422); queue (429 `SALE_BUSY`); per-account limit (409); **holder limit** (409 `PER_ACCOUNT_LIMIT` `HOLDER`); room eligibility of split `pays` members (409 `NOT_ELIGIBLE`, `details.field`); **members-only places** (409 `MEMBERS_ONLY`); quota (409 `SOLD_OUT`). The token may be used for several orders until its `expires_at`. **Holder limit:** for each distinct holder account of the request (a place without `phone` is the buyer's), its places in `RESERVED`/`AWAITING_CASH` orders of the event, plus its `VALID`/`BLOCKED` tickets of the event, plus its places in this request, must be ≤ `per_account_limit`. `details.field` = that account's first place. **Members-only:** each place of a `MEMBERS` category is held by an account with a membership of the organizer, `left_at` null and `joined_at` < the event's `sale_starts_at` (any live member when it is null). `details.field` = the first such place that fails. Holder accounts are locked with the buyer's (per-account lock, UUID order), so both limits are exact. **Lot 5 step 4:** + `promo_code?` (string; absent, null or empty after trimming = none). It is trimmed and uppercased, then must match `^[A-Z0-9]{4,20}$`, else 422 on `promo_code`; this is checked with the body's shape, before admission, with no SQL. After members-only: **promo code** (409 `PROMO_REFUSED`, §Promo codes), then quota. The response + `promo_code` (the normalized text, or null) and `discount_mad` (0 without a code). `total_mad` is after the discount. Split member orders never carry the code. Till sales (`/org/pos/orders`) have no promo field. |
| POST | `/fan/orders/{id}/pay` | `{method: CARD\|WALLET\|CASH_AGENCY, channel?: APP\|WEB}`. Buyer only (404). Order `RESERVED` or `AWAITING_CASH` with `reserved_until > now()`, else 409 `ORDER_EXPIRED` / `ORDER_NOT_PAYABLE`; the order row is locked first. **CARD, WALLET** → `200 {payment_id, method, redirect_url}`: a new PENDING attempt per call; `redirect_url` = `/payments/card/{payment_id}/redirect` for both (the hosted page; the path keeps its Lot 0 name). On an `AWAITING_CASH` order the code stays payable until one method succeeds. **CASH_AGENCY** → `200 {payment_id, method, pay_code, reserved_until, amount_mad}`: `RESERVED` → `AWAITING_CASH`, `reserved_until = least(now + 24 h, refund_cutoff_at)`, one PENDING payment (provider `CASH`) with a new code (§Cash codes). An `AWAITING_CASH` order that already has a PENDING code → the same answer (no new code, hold unchanged). Refused with `METHOD_NOT_AVAILABLE`: `TOO_LATE` if the new `reserved_until` is less than `payments.cash.min-window` (config, default 2 h) away; `CASH_CAP`; `NOT_CONFIGURED`. **Lot 4:** `channel` = the paying client (absent = the order's `channel`). A CARD/WALLET attempt stores it and `/return` lands on it, so a split-pay member order made in the app can be paid on the shop and the other way round. **Lot 5 step 3:** a product order pays like any order. `CASH_AGENCY`: `reserved_until = least(now + 24 h, the product's sales_close_at)` (**3b:** an installment order: `now + 24 h`); `TOO_LATE` per `payments.cash.min-window` as for events; no `CASH_CAP`. |
| GET | `/fan/orders/{id}` | `{id, event_id, channel, status, payment_status, total_mad, reserved_until, paid_at, items[], ticket_ids[]}` (`payment_status`: `SUCCEEDED` if any attempt succeeded; otherwise the latest attempt's status, a `PENDING` **CARD/WALLET** attempt older than 20 min (the late-success window, counted from `redirected_at` when set, else `created_at`) being reported `FAILED`; a `PENDING` cash code is `PENDING`; null before any `/pay`. ## Split pay

| Rule | Value |
| --- | --- |
| Request | In `POST /fan/orders`, a holder with `pays: true` pays for their own place. They need a `phone` that isn't the buyer's (422 on `items[i].holders[j].pays`, `details.reason` `PHONE_REQUIRED`). At least one place has no `pays` (422 on `items`, `NO_BUYER_PLACE`). Refused when `now + sales.split.hold` (config, default 2 h) is at or after `refund_cutoff_at` (422 on the first `pays`, `TOO_LATE`). `pays` is a boolean (`false` = absent). Checks run per holder in place order (name, phone, then `pays`), then `NO_BUYER_PLACE`, then `TOO_LATE`. Each is `VALIDATION_FAILED` with `details.fields{path}` and `details.reason`. |
| Orders | One transaction and one quota reservation for every place. The buyer's order holds the places without `pays`, and its `total_mad` counts only those. There is one **member order** per distinct `pays` phone. Its `user_id` is that phone's account (created if new). It has the same `channel` and event, `group_order_id` = the buyer's order, status `RESERVED` and `reserved_until` = the buyer's. Its items carry that member's places, held by the member (`name` as typed). |
| Limits | At request time the buyer's check counts every place of the request (as today). Each member's `RESERVED`/`AWAITING_CASH`/`PAID` places for the event, plus their new ones, must be ≤ `per_account_limit`, else 409 `PER_ACCOUNT_LIMIT` with `details.field` = `items[i].holders[j]` of that member's first place and `details.held` = the member's places before this request. The buyer's count also includes the places of their member orders still `RESERVED` or `AWAITING_CASH` (unpaid), so an initiator never holds more than `per_account_limit` unpaid places through splits. |
| Hold | The expiry job skips member orders while the buyer's order is `RESERVED` or `AWAITING_CASH`. When the buyer's order expires, its member orders still `RESERVED` expire in the same pass. A member order whose own card or wallet page was opened less than 20 min ago is skipped (§Late success). A member order already `AWAITING_CASH` keeps its own hold. When the buyer's order becomes `AWAITING_CASH`, its member orders still `RESERVED` get the buyer's new `reserved_until` in the same transaction. When the buyer's order becomes `PAID`, every member order still `RESERVED` gets `reserved_until = least(paid_at + sales.split.hold, refund_cutoff_at)` and one `SPLIT_INVITE` (§Notifications), in the settle transaction. From then on each member order expires on its own. |
| Paying | A member pays their order with `/fan/orders/{id}/pay` like any order (card, wallet or cash code), before or after the buyer. Tickets go to the member only. The buyer never pays for a member's place and never sees a member's ticket. |
| Late | A buyer's success after expiry (§Late success) doesn't revive member orders that have expired. |

## Waiting room

| Rule | Value |
| --- | --- |
| Phases | **Lot 5 step 2.** An event has 0–5 rooms, one per **phase** (1, 2, …), contiguous. Phase 1's sale start is `events.sale_starts_at`; later phases have their own `starts_at`. `opens_at` = sale start − `pre_queue_min`. For each phase not `ENDED` and the next phase not `ENDED` after it: `opens_at(next) > sale start(this)` (an `ENDED` phase in between is skipped). | Lifecycle | `SCHEDULED` → `PRE_QUEUE` at `sale_starts_at − pre_queue_min` → `OPEN` when the draw commits at `sale_starts_at` (with `pre_queue_min = 0`, straight to `OPEN`) ⇄ `PAUSED` (organizer) → `ENDED` (organizer, or automatically at `refund_cutoff_at`; terminal). Joins are accepted in `PRE_QUEUE`, `OPEN` and `PAUSED`. | Tick | Every second (`rooms.tick`), each instance takes the live rooms with `for no key update skip locked`, so one instance handles a room per tick (joins insert with the FK's `for key share`, which that lock doesn't block). Daily: delete entries 30 days after the event's `starts_at`. Each room ticks on its own row (it reads the next phase's `opens_at` without a lock). At the room's first ranking tick, `measured_rate_per_min` = `admission_rate_per_min` (a seed until the first 60 s re-mark). |
| Memo | Each instance reads the non-`ENDED` rooms once a second (`rooms.memo-ttl`, 1 s): event id → its rooms not `ENDED`, by phase (each with `id`, `phase`, `label`, status, sale start, `pre_queue_min`, counts, `admission_rate_per_min`, rule). The current phase is computed from the memo and the clock. The poll and the admission check read only this memo. It may be 1 s behind the database. |
| Queue token | JWT HS256 with `ROOMS_TOKEN_SECRET` (≥ 32 bytes; separate from the fan JWT secret). A poll whose token has `rnk` reads nothing from the database. A token without `rnk` reads the entry once per poll until it is ranked, then gets a token with `rnk`. |
| Admission | A poll that sees `rnk ≤ admitted_through` sets `admitted_at = now()` `where admitted_at is null` (one write per admitted fan). Fan JWTs and room tokens are never accepted for each other. No phone, name or device id in any token. |
| `poll_after_s` | `PRE_QUEUE`: seconds to `sale_starts_at` + a uniform 0–20 s jitter, capped at 30. `WAITING` unranked: 2. `WAITING` or `PAUSED`: `estimated_wait_s` < 20 → 2; < 120 → 5; else 15; ± 20 % jitter. `ADMITTED`, `EXPIRED`, `ENDED`: 0 (stop). Clients never poll faster, and stop in the background. |
| Eligibility | Checked at join, against the current phase's rule and the event's organizer: `min_account_age_days` → `users.verified_at` not null and ≤ `sale_starts_at − n days`. `member_joined_before` → a membership with `left_at` null and `joined_at` < the date. `min_events_attended` → `events_attended` (§Fan `/fan/me/membership`) ≥ n. |
| Device | `device_hash` = HMAC-SHA256(`ROOMS_TOKEN_SECRET`, "device\|" + `device_id`). Entries of other accounts in the room with the same hash ≥ `rooms.device-limit` (3) → `QUEUE_DEVICE_LIMIT`. Soft (no lock). |
| Limits | **Per IP, joins only:** entries of the room with the caller's `ip_hash` (HMAC-SHA256(`ROOMS_TOKEN_SECRET`, "ip\|" + client IP, resolved through trusted proxies only)) and `joined_at` in the last 5 min ≥ `rooms.ip-limit-5m` (300; 0 = off) → `QUEUE_RATE_LIMITED` `IP`, `retry_after_s` 60. Soft (no lock). **Per entry, polls:** one per `rooms.poll-min-interval` (1 s) per instance, kept in memory and checked after the signature → `QUEUE_RATE_LIMITED` `POLL`, `retry_after_s` 1. With N instances an entry can poll at most N times a second. No other per-IP limit in the API; a CDN/WAF may add one in front. |
| Fairness | `draw_key` = 8 bytes from a CSPRNG at join, never returned. Ranks are dense and unique per room. `admitted_through` only grows. A rejoin goes to the back. Join is idempotent per account. |

Answers: `POST /fan/orders/{id}/pay` → `200`. A callback with a missing, bad or tampered signature →
401 `UNAUTHORIZED` with a fixed message and empty `details`, nothing written. `/redirect`, `/return`
and the simulated gateway page are browser pages (FR HTML, e.g. the 410), not the JSON error shape;
an unknown `payment_id` on `/redirect` is the JSON 404. A success on a `RESERVED` order whose hold
has passed but that the expiry job hasn't swept yet is a normal `PAID` (the places are still held).

Late success: expiry skips orders with a `PENDING` CARD/WALLET payment whose hosted page was opened (`redirected_at`, set by `/payments/card/{id}/redirect`) less than 20 min ago; an attempt never redirected doesn't hold the order. A success after
expiry (card, wallet or cash network) re-reserves the quota atomically → `PAID`; if no quota is left the order stays `EXPIRED`,
the payment is `SUCCEEDED`, and `audit_log` gets `payment.refund_required` (manual refund) with reason `SOLD_OUT`,

`AMOUNT_MISMATCH` (an approved callback whose amount differs from the payment: payment `FAILED`,
order stays payable, the charged amount must be refunded).

## Organizer

Every `/org/*` call except `/org/auth/*` and `/org/me` needs `X-Organizer-Id`. The server checks
for an active `staff` row (user_id = token subject). Lot 0 roles: `ADMIN`, `OPS` read and write;
`FINANCE` read only; `GATE`, `SUPERVISOR` get 403. A missing or malformed `X-Organizer-Id` → 400
`BAD_REQUEST`; no active staff row for it → 403 `FORBIDDEN`. Lot 2: devices, staff, assignments and close are ADMIN/OPS; `/live` and `/reconciliation` are also FINANCE (read). GATE/SUPERVISOR still get 403 on `/org`: they only use the scanner. Refund: ADMIN. `GET /org/refunds` and the ticket lookup (`POST /org/events/{id}/tickets/search`): ADMIN, OPS, FINANCE. `POST /org/refunds/{id}/done`: ADMIN, FINANCE (FINANCE's first write). `/org/finance/cash`: ADMIN, OPS, FINANCE. `/org/pos/**`: ADMIN, OPS, CASHIER. Fans and staff use the same OTP mechanism, counted per audience (`otp_challenges.audience`): a
code verifies only on the endpoint family that requested it, and staff requests never use up a fan's
limits. Staff codes get the same per-phone limits as fans (3 per 10 min, 10 per 24 h, lockout after 15
failures in 24 h — founder decision Q14) plus the org per-IP limit, all **silent**: over a send limit
`/org/auth/otp` still answers 202 and sends nothing; a locked phone on `/org/auth/verify` answers
`OTP_INVALID` like a wrong code. Anyone can lock a staff phone out for 24 h; that cost is accepted.
IPv6 clients are bucketed per /64 for the per-IP limits. A bearer token sent
to `/fan/auth/**` or `/org/auth/**` is ignored. The failure lockout (fan and staff) counts failures on challenges
created in the last 24 h, so it can lift up to 5 min before the oldest failure is 24 h old.

## Gate auth

```
X-Device-Id:        <device uuid>        (absent only on POST /gate/devices/enrol)
X-Device-Time:      <unix ms>            (device clock + server offset)
X-Device-Signature: base64url (no padding) of the DER ECDSA P-256 / SHA-256 signature over:

"JMH-GATE-1" LF METHOD LF PATH LF X-Device-Time LF lowercase-hex(SHA-256(body))
```

| Rule | Value |
| --- | --- |
| PATH | Raw path + query exactly as sent, including `/v1` (`/v1/gate/events/12/manifest?since=3`) |
| X-Device-Time | Decimal digits, no leading zero (`0` or `[1-9]` followed by up to 14 digits), signed exactly as sent; anything else → 401 |
| body | Raw request bytes (requests are not compressed), at most 1 MiB (larger → 413 `BAD_REQUEST` before any signature check); empty body → SHA-256 of the empty string |
| Server order | Device known (enrol: key from the body) → signature → \|time − now\| ≤ 5 min (else `DEVICE_CLOCK_SKEW`) → status `ACTIVE` (except enrol, and `GET /gate/events` which answers 403 for `PENDING`). Then `devices.last_seen_at = now()` |
| Replay | Accepted within the 5-min window: GETs are reads, scans are idempotent, enrol is idempotent per key; TLS throughout |
| `server_time` | In every gate JSON response (RFC 3339, ms). The device offset = `server_time` − the midpoint of request send and response receive |

```
reentry	{NONE|ONE_EXIT}
rows	{ticket rows in this version, full count}
Z	{zone_id}	{code}	{name}                         every zone of the venue, by zone_id
G	{gate_id}	{code}	{name}	{zone_id,zone_id,...}   every gate of the venue, by code; zone ids ascending
T	{ticket_id}	{zone_id}	{status}	{holder_initials or empty}
```

Full: one `T` per ticket of the event, by `ticket_id`. Delta: `T` only for tickets added or whose status changed since `since` (Z and G lines always complete). The device applies a delta only if its version equals `since`; afterwards its row count must equal `rows`, otherwise it refetches the full manifest. Status → result: VALID → continue, CANCELLED/REFUNDED → `CANCELLED`, BLOCKED → `BLOCKED`. **Lot 5 step 3b:** `T` status = the ticket's effective status (§Passes Effective status), so a suspension or a reactivation reaches devices as an ordinary delta. Format unchanged. No name, phone or ID number ever goes in the payload. 45,000 rows ≈ 2.6 MB of text, about 1.2 MB gzipped (02:66 says under 1 MB: accepted).

## Gate reports

Admitted = `OK` or `OVERRIDE`. Canonical = per ticket, the admitted scan with the earliest `device_time` (tie: lowest `scan_id`). Refused = any other device result. `sold` = tickets `VALID` (blocked, refunded and cancelled tickets are not sold).

| --- | --- |
| `GET /org/events/{id}/live` | `{event_id, status, starts_at, server_time, sold, entered, rate_per_min, rate_per_min_prev, refused:{total, by_result:{DUPLICATE: n, …}}, duplicates_late, overrides:{total, cap_per_device: 20, by_device:[{device_id, label, count}]}, gates:[{gate_id, code, zone_codes[], devices_total, devices_online, entered, refused, overrides, rate_per_min, last_sync_at}], devices_stale:[{device_id, label, gate_id, gate_code, last_seen_at}]}`. `by_result` lists refused result codes (never `OK`/`OVERRIDE`) with a count > 0 only. `entered` = tickets with a canonical scan (per gate: canonical scans at that gate). `duplicates_late` = admitted − canonical. `rate_per_min` = admitted scans with `device_time` in the last 5 min ÷ 5 (integer); `_prev` = the 5 min before that. ## Token (shared by `packages/core` and the backend)

```
bytes:  version(1) | event_id(4, BE) | ticket_id(16) | zone_id(2, BE) | [slot(4, BE)] | tag(16)
v1 static:   tag = HMAC-SHA256(K_e, version|event_id|ticket_id|zone_id)[0:16]
v2 rotating: K_t = HMAC-SHA256(K_e, ticket_id); slot = floor(unix/30)
             tag = HMAC-SHA256(K_t, version|event_id|ticket_id|zone_id|slot)[0:16]
encoding: base64url, no padding
```

Acceptance on the scanner: v2 valid if `|slot - now_slot| <= 1` (server-time-corrected clock).

### Test vectors (`docs/token-vectors.json`, generated by the backend)

`TokenVectorsTest` (backend) builds 10 static and 10 rotating vectors from fixed inputs, including the edge values and the 6 interim cases (hard-coded in the test). Locally, if the file is absent or `-Djomhor.writeVectors=true` is set, it writes `docs/token-vectors.json`; in CI (`CI` set) a missing file fails; otherwise it fails when the committed file differs. `packages/core` fails, rather than skipping, when the file is missing.
Format:
`[{k_e, event_id, ticket_id, zone_id, slot?, expected_token}]` for 10 static and 10
rotating tokens. Field encodings: `k_e` lowercase hex (64 chars); `event_id`, `zone_id`,
`slot` JSON integers (`slot` absent for v1); `ticket_id` canonical lowercase UUID string;
`expected_token` base64url without padding. Include the edge values (`event_id` 0xFFFFFFFF,
`zone_id` 0xFFFF, `slot` 0xFFFFFFFF). `packages/core` golden-tests against the same file. Regenerate with `./gradlew test -Djomhor.writeVectors=true` (backend) only when
the layout changes; both `TokenVectorsTest` and the `packages/core` golden test read the committed file.

## Gate vectors

`GateVectorsTest` (backend) writes `docs/gate-vectors.json` under the same rules as the token vectors (CI fails if it is missing or differs): `{signing:[{method, path, time, body, expected_string, expected_body_sha256}], fingerprints:[{public_key, fingerprint}], manifest:[{public_key, payload, signature}], pins:[{pin, verifier, ok}]}`. Ed25519 is deterministic, so a fixed test key gives fixed signatures. `apps/scanner` golden-tests against it.
